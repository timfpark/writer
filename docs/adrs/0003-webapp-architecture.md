## Status

Accepted on 2026-11-19.

[ADR 0004](./0004-api-conventions.md) decides versioning and naming below
`/api/`, which this record leaves open: every route lives under `/api/v1/`.

## Decision summary

* Build `webapp/` as a client-rendered React 19 single-page application
  compiled to `webapp/dist/` with Vite 8 on Node.js 26 (`engines` matching
  `.devcontainer/`, `.npmrc` setting the registry proxy, `save-exact=true`,
  `engine-strict=true`, and `ignore-scripts=true`).
* Type-check with TypeScript 6.0 (`strict`, `noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, `verbatimModuleSyntax`).
* Generate contract types from `service/openapi.json` into
  `webapp/src/api/generated/schema.d.ts` via `npm run api:generate` (`api:check`
  in the gate), and call the API only through `webapp/src/api/client.ts` using
  `openapi-fetch` with same-origin paths.
* Bind Vite's dev server to `127.0.0.1:5173` (`strictPort`) and proxy `/api/`
  to `http://127.0.0.1:8080` without path rewriting.
* Enforce quality in `tools/check` (after `service`) with `npm ci`,
  `api:check`, Prettier 3 (excluding Markdown and generated files), Oxlint with
  `--type-aware --deny-warnings`, `tsc`, Vitest 5 (`jsdom`), and `vite build`.

## Context

[ADR 0001](./0001-monorepo-structure.md) makes the webapp a TypeScript and
React client that depends on the service only through the committed OpenAPI
document. Its client is generated into `webapp/src/api/generated/`, committed,
and checked for freshness. Its Node.js version is pinned in `package.json`
`engines`, its packages install through the
`https://packagefeedproxy.microsoft.io/npm/` proxy, and its `tools/check` phase
runs after the service's. ADR 0001 leaves the build tool and generator to this
decision.

[ADR 0002](./0002-service-architecture.md) emits that document as OpenAPI 3.1.0
JSON at `service/openapi.json`, binds the service to `127.0.0.1:8080`, and
streams incremental agent results over server-sent events (SSE). It adds
cross-origin support only if this decision requires it. It moves the contract
to OpenAPI 3.2 once the webapp's generator reads 3.2.

The first deployment is local: one user, one service process, and a browser on
the same machine. [Backlog 7](../backlog/0007-webapp-foundation.md) builds the
first page, which shows the service's health. Later stories add editing and
streamed pair-writer suggestions.

An earlier project chose React, Vite, openapi-typescript, ESLint, Prettier,
Vitest, and Playwright for a similar client, alongside styling, authentication,
static serving, and content security policy decisions for a hosted financial
application. We reuse its build and generator reasoning, revisited against
November 2026 releases. Its other decisions answer requirements Writer does not
have yet and are left to the stories that need them.

A prototype built outside the repository, on Node.js 26.13.1 in a container,
installed the selected releases through the npm proxy with install scripts
disabled. It generated a client from a synthetic OpenAPI 3.1.0 document shaped
like utoipa's output, then ran the format, lint, type, test, build, and
freshness checks. Its development server proxied JSON and an SSE stream to a
stand-in service on `127.0.0.1:8080`, delivering each event as the service wrote
it, and refused to start when port 5173 was taken. Findings that shaped this
decision are noted where they apply.

## Decision drivers

* A thin, client-rendered React application calling one local service
* A generated client that reads OpenAPI 3.1 and fails the gate when stale
* Streamed responses reaching the browser as the service writes them
* No cross-origin configuration in the service for local development
* Few dependencies, exact versions, and no package install scripts
* Checks fast and deterministic enough for `tools/check` on every commit
* Tools that contributors and coding agents already know

## Considered options

### Build tool

1. Vite 8 bundles with Rolldown and transforms with Oxc since 8.0, released in
   March 2026. It supplies a development server with hot module replacement and
   a built-in proxy, an official React plugin that no longer needs Babel, and
   configuration that Vitest shares. It has by far the largest adoption of the
   options here, about 290 million weekly downloads.
2. Rsbuild 2 on Rspack is a fast Rust bundler with a webpack-compatible plugin
   API, a development server, and a proxy. Its compatibility with webpack
   solves a migration problem we do not have, its ecosystem is roughly a
   hundredth of Vite's, and tests would not share its configuration.
3. Webpack 5 is mature but configuration-heavy and slower, with nothing to
   offer a new project that Vite lacks.
4. Vite+ 1, VoidZero's MIT-licensed command-line tool, wraps Vite, Vitest,
   Oxlint, and the oxfmt formatter behind one `vp` command and one manifest
   entry. It ties every tool's upgrade to a Vite+ release, ships the pre-1.0
   oxfmt, and puts a wrapper between contributors and the commands each tool
   documents.
5. Frameworks with a server runtime, such as Next.js, React Router's framework
   mode, and TanStack Start, add server rendering and server functions that
   duplicate the service's role and add a second server process.
6. Bun's bundler requires a second JavaScript runtime alongside Node.js.

### API client generator

Every option here reads OpenAPI 3.1. Adoption is npm's weekly download count in
November 2026.

| Generator                          | Output                                                                 | OpenAPI 3.2                                                    | Activity and adoption                                                    |
|------------------------------------|------------------------------------------------------------------------|----------------------------------------------------------------|--------------------------------------------------------------------------|
| openapi-typescript + openapi-fetch | One file of path and schema types; a small runtime client typed by it  | Accepts a 3.2 document but ignores `itemSchema`; request open  | About 18 million each; last release February 2026                        |
| hey-api openapi-ts                 | A function per operation plus a client, with typed SSE helpers         | No; request open                                               | About 8 million; pre-1.0 with breaking changes in most minor releases    |
| Orval 8                            | Functions per operation for fetch, Axios, or TanStack Query, and mocks | Not documented                                                 | About 4 million; weekly releases                                         |
| Kubb 5                             | A plugin pipeline producing types, clients, Zod schemas, and hooks     | Documented as read                                             | About 0.6 million; frequent releases                                     |
| OpenAPI Generator `typescript-*`   | Classes per tag                                                        | Not relevant                                                   | Needs a Java virtual machine the development container does not carry    |

Generating only types keeps the committed output to one file whose diff shows
exactly how the contract changed. openapi-fetch takes paths, methods,
parameters, and bodies from those types, so the compiler rejects a call the
contract does not allow without per-operation generated code. hey-api, Orval,
and Kubb generate a function per operation, which adds review surface and, in
Orval's and Kubb's case, configuration for targets we do not use. Kubb is the
only option that reads OpenAPI 3.2 today, but has the smallest user base.

openapi-typescript and hey-api build their output with the TypeScript compiler's
JavaScript API, which TypeScript 7.0 does not provide. Orval and Kubb do not
depend on it.

### Cross-origin access

1. A development-server proxy serves the application and the API from one
   origin, with Vite forwarding API paths to the service. There is no
   cross-origin resource sharing (CORS) configuration, no preflight request,
   and no service URL in the browser bundle. Cookies, if authentication later
   uses them, stay same-origin. The proxy needs a path prefix that separates
   API routes from application routes.
2. CORS has the service allow exactly the development server's origin while the
   client uses an absolute service URL fixed at build time. The service gains a
   `tower-http` CORS layer and an origin to keep in step, non-simple requests
   pay a preflight, and any later same-origin hosting changes the client's
   configuration.

### Development server port

Port 5173 is Vite's default, so documentation, examples, and agents' knowledge
apply without an override, and it is distinct from the service's 8080. No other
port offers an advantage.

### Linter

1. Oxlint 1 implements the TypeScript, React, React Hooks, JSX accessibility,
   import, and Vitest rule sets natively in Rust. Its type-aware rules, run by
   `oxlint-tsgolint` on TypeScript 7, cover 59 of typescript-eslint's 61
   type-aware rules and have been stable since July 2026. It needs two
   packages. In the prototype it linted the application in under 100 ms and
   reported a floating promise and a wrong effect dependency.
2. ESLint 10 with typescript-eslint has the largest rule and plugin ecosystem.
   typescript-eslint supports TypeScript only below 6.1, and
   `eslint-plugin-jsx-a11y`, last released in October 2024, does not declare
   ESLint 10 support. The setup needs six or more packages whose peer ranges
   must stay aligned.
3. Biome 2 lints and formats with one binary. Its type-aware rules infer types
   without the TypeScript compiler, so they are fewer and less exact, and its
   formatter's output is close to Prettier's but not identical.

### Formatter

1. Prettier 3 is stable and the formatter most contributors and agents know.
2. oxfmt targets Prettier-compatible output much faster, but is still before
   1.0.
3. Biome's formatter is covered above.

### TypeScript version

1. TypeScript 7, the native compiler released in July 2026, is the fastest, but
   7.0 has no JavaScript compiler API. openapi-typescript declares a
   TypeScript `^5.x` peer and builds its output with that API. Peer
   dependencies resolve once per project, so npm cannot give it a separate
   copy; the prototype's install failed with `ERESOLVE`.
2. TypeScript 6.0 is the last release with the JavaScript API and the bridge to
   7: it deprecates what 7 removes. openapi-typescript runs on it once an npm
   `overrides` entry widens its peer range; the prototype generated correct
   types this way.
3. TypeScript 5.9 satisfies every peer range without an override, but starts
   two major versions behind and leaves the move to 6.0 for later.

### Test runner

1. Vitest 5 reuses Vite's configuration and transforms, runs ES modules
   natively, and pairs with jsdom and React Testing Library for components.
2. Jest needs its own transform configuration and handles ES modules less
   directly.
3. Browser end-to-end testing with Playwright exercises real engines, but the
   first page needs only a component test and a manual check. It is deferred.

## Decision

### Application shape

Build a client-rendered single-page application with React 19 and TypeScript,
compiled to static files in `webapp/dist/`. Do not add server rendering, React
Server Components, or a framework server; the service is the only server.
Routing, styling, server-state caching, and authentication are chosen, and
recorded in an ADR, by the first story that needs them.

### Build tool and runtime

Use Vite 8 with `@vitejs/plugin-react` 6. Start on `vite` 8.3.8,
`@vitejs/plugin-react` 6.3.0, and `react` and `react-dom` 19.3.1. Resolved
versions live in `webapp/package-lock.json`; upgrading within these choices is
a dependency change, not a new decision.

Use Node.js 26, the active long-term support line. Pin `engines.node` in
`webapp/package.json` to exactly the version the development container pins,
26.13.1 at acceptance, and change both together. `webapp/.npmrc` sets:

* `registry=https://packagefeedproxy.microsoft.io/npm/`
* `save-exact=true`, so every direct dependency has an exact version
* `engine-strict=true`, so installing on another Node.js version fails
* `ignore-scripts=true`, so no package runs code at install time

No package in the prototype's dependency tree has an install script. If a later
dependency needs one, name it in `webapp/AGENTS.md` and run its step
explicitly rather than enabling scripts for every package.

### API client

Generate types with openapi-typescript from `service/openapi.json` into one
file, `webapp/src/api/generated/schema.d.ts`, and call the service with
openapi-fetch. Start on `openapi-typescript` 7.13.0 and `openapi-fetch`
0.17.0.

* `npm run api:generate` regenerates the file. Output is deterministic: two
  runs in the prototype produced identical bytes.
* `npm run api:check` runs the generator with `--check` and never writes. On a
  mismatch it exits 1 with a message naming
  `webapp/src/api/generated/schema.d.ts` and `npm run api:generate`; the
  generator's own message names neither, so the script adds them.
* One hand-written module, `webapp/src/api/client.ts`, creates the client. It
  uses the page's origin as the base URL and looks up `fetch` on each call,
  because openapi-fetch otherwise captures the global `fetch` when the client
  is created and tests cannot replace it. Components call the service only
  through this module.
* Responses are not validated at run time; the types assume the service honors
  the contract. Both subsystems ship from one repository and one gate, and
  ADR 0002's router tests decode every documented response, so a runtime
  validator would guard against a mismatch the gate already prevents.
* For an SSE endpoint, openapi-fetch exposes the raw response stream. Type each
  event with the named schema ADR 0002 registers under `components`, which the
  generator exports. The story that first consumes a stream chooses how to
  read it.

The prototype confirmed that openapi-typescript 7.13.0 reads OpenAPI 3.1:
JSON Schema type arrays such as `["string", "null"]`, `const`, `enum`, and
`oneOf` with a discriminator all produced the expected TypeScript types. It
does not read OpenAPI 3.2. It accepts a 3.2.0 document without error, but
ignores `itemSchema` and types the stream's body as `unknown`, so ADR 0002's
trigger for moving to OpenAPI 3.2 remains unmet.

### TypeScript

Use TypeScript 6.0, starting on 6.0.3, and run `tsc` without emitting over the
application, its tests, and its configuration files. Enable `strict`,
`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and
`verbatimModuleSyntax`, with `moduleResolution` set to `bundler` and `jsx` to
`react-jsx`. Use no option that 6.0 deprecates, so the configuration carries
to TypeScript 7 unchanged; `oxlint-tsgolint`, built on TypeScript 7, loaded the
prototype's configuration without error.

Add this `overrides` entry to `webapp/package.json` so openapi-typescript
accepts the project's TypeScript, and remove it once openapi-typescript
declares support for the version in use:

```json
"overrides": {
  "openapi-typescript": { "typescript": "$typescript" }
}
```

### Development server and service access

Bind the Vite development server to `127.0.0.1:5173` with `strictPort`, so it
fails when the port is taken rather than choosing another one. Contributors
open `http://localhost:5173`. In the development container, `forwardPorts`
lists 5173, and the editor forwards it to the container's loopback interface.

The development server proxies every request whose path starts with `/api/` to
`http://127.0.0.1:8080`, without rewriting the path, so a path in the browser
is the path in the contract. The target uses the IPv4 literal because the
service binds only `127.0.0.1`, and `localhost` can resolve to `::1` first. If
the service's port becomes configurable, the override is an environment
variable without the `VITE_` prefix, so the service URL never enters the
browser bundle.

This decision constrains the service:

* Every API route lives under `/api/`, and nothing else does. Paths outside
  `/api/` belong to the webapp. Versioning and naming below `/api/` remain
  with the API conventions decision ADR 0002 lists as a follow-up.
* The service adds no CORS layer; ADR 0002's conditional cross-origin support
  is not needed. A page at another origin cannot call the API, which is
  correct for a single local user.

The client's base URL is the page's origin, so the same build works behind any
host that routes `/api/` to the service. Serving the built application is left
to a hosting decision, which keeps that routing or revisits this one.

### Quality checks

* **Lint:** Oxlint with type-aware rules through `oxlint-tsgolint`, starting
  on `oxlint` 1.93.0 and `oxlint-tsgolint` 7.0.2007, configured in
  `webapp/.oxlintrc.json`. Enable the `typescript`, `react`, `jsx-a11y`,
  `import`, and `vitest` plugins and the `correctness` and `suspicious`
  categories as errors, plus the React Hooks rules and
  `typescript/no-floating-promises`. Run with `--type-aware` and
  `--deny-warnings`. `tsc` remains the authority on type errors, so do not
  enable Oxlint's `--type-check`.
* **Format:** Prettier 3 with its default options, starting on 3.10.1.
  `webapp/.prettierignore` excludes the generated client and Markdown files.
  Markdown style belongs to the repository-wide lint in
  [.markdownlint-cli2.jsonc](../../.markdownlint-cli2.jsonc), and Prettier
  would rewrite the `*` list markers this repository uses.
* **Test:** Vitest 5 with jsdom and React Testing Library, configured in
  `webapp/vite.config.ts` and run once with `vitest run`. Start on `vitest`
  5.1.0, `jsdom` 31.0.0, and `@testing-library/react` 16.3.3. Tests sit next
  to the code they test as `*.test.ts` or `*.test.tsx`, replace `fetch` rather
  than calling a real service, and need no network access.

The generated client is excluded from lint and formatting, but not from type
checking.

The `webapp` phase of `tools/check` runs these commands in `webapp/`, after
the `service` phase:

```bash
npm ci
npm run api:check
npm run format:check
npm run lint
npm run typecheck
npm run test
npm run build
```

The phase fails when any command fails. A missing `node` or `npm`, or a Node.js
version other than the one `engines` pins, is a prerequisite error with exit
status 2. The gate does not run `npm audit`: it queries an advisory service
over the network, which the proxy rate-limited during the prototype, so its
result would depend on the network rather than the change. Dependabot alerts,
adopted in ADR 0001, report advisories instead.

## Consequences

Positive outcomes:

* Development uses one origin, the service carries no CORS configuration, and
  the browser bundle holds no service URL.
* A contract change appears as a diff to one generated file, and a stale
  client fails the gate with a named file and the command that fixes it.
* Rust-based building and linting keep the `webapp` phase fast: in the
  prototype, the build took under 100 ms and type-aware lint under 100 ms.
* The prototype installed 124 packages, none with an install script.

Trade-offs and risks:

* The `/api/` prefix constrains the service's paths before the API conventions
  decision is made.
* Two TypeScript versions are in use: 6.0 for type checking and generation,
  and 7 inside `oxlint-tsgolint`. They can disagree in rare cases, and the
  `overrides` entry is a workaround to remove when possible.
* openapi-typescript has not released since February 2026 and reads neither
  TypeScript 7 nor OpenAPI 3.2. If it stalls, it blocks both moves. Because
  only types are generated, replacing it changes one generated file and
  `client.ts`, plus call sites if the replacement generates per-operation
  functions.
* Without runtime validation, a service that broke its contract outside the
  gate would surface as a type-unsafe value rather than a clear error.
* Oxlint has fewer third-party rules than ESLint. A needed rule it lacks
  means revisiting the linter choice.
* No browser end-to-end tests run until a story adds them.

## Revisit triggers

* Move to TypeScript 7 and remove the `overrides` entry when openapi-typescript,
  or its replacement, runs on it.
* Replace the generator if openapi-typescript has no release supporting
  TypeScript 7 or OpenAPI 3.2 when the webapp needs either, or stops being
  maintained. Kubb reads OpenAPI 3.2 today. A generator that reads 3.2 also
  meets ADR 0002's trigger for moving the contract to 3.2.
* Add runtime response validation when the webapp may run against a service
  built from a different commit, or reaches a service beyond loopback.
* Revisit the proxy when a hosting decision serves the webapp and the service
  from different origins.
* Consider oxfmt in place of Prettier once it reaches 1.0.

## Follow-up decisions

* Routing, styling and components, and server-state caching, made by the first
  story that needs more than one view
* Browser end-to-end and automated accessibility testing
* Serving the built application, content security policy, and hosting beyond
  loopback, alongside the service's hosting decision
* Authentication and session handling, alongside the service's authentication
  decision
